# Phase 6B preregistration — static baseline validation

Written before the 6B simulations. Phase 1–5 inputs remain read-only; all outputs stay in this directory.

## Questions and criteria

- **All-up controls:** static must achieve PDR $\geq 0.99$ on an all-up line and an all-up ladder. A failure means the static implementation is not an upper ceiling.
- **Dynamic line controls:** evaluate the same three 6A cells using the 121 dB receive-sensitivity threshold and continuous linear-in-dB channel interpolation. The static usable-route mode recomputes its route at every interpolated edge threshold crossing. Report absolute PDR-minus-effective-uptime error for every realization. Predeclare tolerance as 0.05 absolute PDR; all three cells must have mean error $\leq 0.05$ and no individual realization may exceed 0.10 to pass this check.
- The all-up line input contains 60 copies of the five-node line topology from the serialized Phase 5 line trace. The all-up ladder input is the read-only Phase 1 static ladder trace. Same Wi-Fi, traffic, loss, and PHY settings as Phase 6A; line and ladder controls use 0.25 fps to give long all-up observation windows. Dynamic cells use 1 fps and the Phase 6A traffic window.

## Exact batch and runtime basis

- Five ns-3 graph-run invocations, one static protocol replay each: all-up line, all-up ladder, and one each for the three 6A dynamic cells.
- The latest same-build static-only replay measured 0.20 s wall time; estimate is 5 x 0.20 = 1.0 s of simulation runtime, excluding process/startup overhead. No campaign beyond this gate is included.

## Execution addendum (written after the five runs)

The line control input contains 70 repeated matrices, not the 60 specified above. Provenance review found that it was hand-authored directly as a repeated-matrix CSV; it was not generated by the Phase 5 graph/export pipeline. The saved creation content matches the input file byte-for-byte, but the record does not explain why 70 rather than 60 matrices were authored. This is an input deviation in the 6B control only, not a change to Phase 5/6A traces. The line run had `warmup=0`, `fps=0.25`, applied 70 frames, and spanned 276 s (timestamps 0–276); it is not a warm-up artifact. The dynamic usable-route runs used `warmup=45`, `fps=1`, and 60 source frames, with active traffic from 45.1 to 104.0 s (58.9 s), so the all-up and dynamic runs do not share the same replay timing settings. The all-up line result is a `static` protocol row (PDR 1.000; 1,684/1,684 application packets delivered), not an OLSR or DSDV result. The PDR criterion is met on this hand-authored all-up input, but this run does not test Phase 5 serialization and is not a conforming execution of the planned 60-frame line control. The all-up ladder also ran `static` and achieved PDR 1.000. Actual simulator-reported wall times were 1.932 s (line all-up), 2.151 s (ladder all-up), 0.214 s (path-life 0.5 dynamic), 0.294 s (path-life 0.7), and 0.392 s (path-life 0.9), total 4.983 s excluding ns-3 command startup. The original runtime estimate was based on the short dynamic trace and underestimated long all-up controls.

The two all-up controls each delivered every offered packet (static PDR 1.000). Dynamic usable-route static PDRs are 0.369, 0.661, and 0.869 for graph 0001 in the three respective cells. Compare these with the corresponding validated effective-uptime values in the 6A analysis; the dynamic baseline criterion does not pass. Therefore static is **not** a validated ceiling. The `usable` mode is opt-in; legacy static frame routing remains the default.
