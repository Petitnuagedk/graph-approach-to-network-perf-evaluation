## Read-only follow-up: Phase 6 traffic-window warm-up offset

The 6A/6E scalar traffic-window oracle is correctly trace-relative, not misaligned. ns-3 prepends 45 frames in `warmupMode=first`, shifts the original trace timestamps by 45 s, starts traffic at 45.1 s, and stops at the last shifted source-frame timestamp. For 60 source frames at 1 fps, its absolute interval `[45.1, 104.0]` is exactly the source-trace interval `[0.1, 59.0]` translated by 45 s. Integrating the same trace in both coordinate systems produced identical frame uptime (0.490662139219) and usable uptime (0.664427548535); differences were 0 and 3.3e-16 respectively. The saved ns-3 diagnostic reports 0.490662139 and 0.664427549 over 45.1–104.0 s, matching the recomputation. The source run is documented in the [6A diagnostic config](../phase6/6A/regression/with_diagnostics/config.json) and [C++ oracle diagnostic output](../phase6/6A/regression/with_diagnostics/oracle_diagnostics_static.csv).

The coordinate distinction is handled downstream too: [the 6A analysis](../phase6/6A/analyze_6a_corrected.py) adds 45 s to usable intervals before testing absolute packet-event timestamps. The 6E analysis uses only the scalar trace-relative integration and does not compare those relative intervals to absolute event times. This was a source/data audit and local recomputation only; no simulator run or experimental-data change was made.
